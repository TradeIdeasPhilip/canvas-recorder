# IndexedDB to Code

Some projects will be mostly bound by their json files.  TypeScript code provides defaults to get The Designer started.  And that’s good.  But other times it would be nice if the tools would help me push the changes back into the TypeScript code so I only have one copy.  Some projects are mostly about code.

When this feature is enabled, the code should save the typescript defaults on every restart.
Add a 5 second delay for debouncing.
If you want this feature you have to initiate it and say where you want your file saved.
But once you do that, the setting is sticky.
Until the user disables the request, we store the file handle to indexedDB, then we use that file handle to write the result.

Visible status:  “Off”, “Pending”, “Saved”, “Error”.  That’s next to the button that enables or disables this feature.
<label><input id=“...” type=“checkbox”>Save defaults:  <span id=“…”></span></label>
The status of this checkbox is *only* stored in IndexedDB.
We have to use that to save the file handle.
We save most of our GUI settings in sessionStorage, but there is no reason to duplicate this one.
If there is a file handle in the database, the box will be checked and we try to do the automatic  save.
The checkbox should be disabled while we are waiting for IndexedDB to give us the saved status, for simplicity, initialization will be complete before the user is allowed to interact, disable in HTML to be first and failsafe.
Unchecking the checkbox deletes the handle from IndexedDB and immediately changes the status on the screen.
Checking the checkbox gives the user a save dialog box and if they don’t hit cancel the program saves the file handle and immediately attempts the save the TypeScript Defaults (which we are already saving in memory).  The status output should immediately change to “pending” and eventually change to “Saved” or “Error”.

This file could be useful in a lot of contexts, not just the use case of rolling the changes back into the code.
Especially in git where we have a history.
This file is redundant, as it was generated by the code.
But it’s a *summary* of the GUI, possibly in an easier language to read.
This file is useful on its own,

We already have a way to save the current state to a JSON file.
So it will be easy to diff those two files.
See what has changed since the last time I manually copied things from the file back into the code.
The first step would be to decide which changes were intentional and should be permanent.
(Like a normal `git diff` before committing, when a project is all hand typed code.)
Then a human or an AI could merge those changes back into the code.
When you think you are done, run the code and then do a diff again to see if you missed anything.
You don’t have to wait, you can rerun the program each time you make a single change and look at the diffs to see how much the saved defaults file looks like the last commit and how much it looks like the output of our normal save.

In a lot of cases the code is very simple and we can just copy the value right out of the json diff and right into a constructor.
That is certainly the common case.
(Ideally we’d use the smaller version of the constructor when a scheduled value has only one keyframe and the time is 0, but still ridiculously simple.)
Sometimes the constructors are filled by running arbitrary code.
In those cases we’d have to think more to make the code match the current state.
In the general case the problem is literally impossible, i.e. halting problem, but we’re focused on code that we understand.
Based on my past experiences, I might use the Visual Editor to change a few specific keyframes, but I won’t finish the job because it would be too much work and the typescript code could do it more efficiently and precisely.
I.e. if it’s not just copy from the json file and paste into the constructor, then there’s a good chance that the json file isn’t complete anyway, and there are additional instructions hiding in the user’s head.
